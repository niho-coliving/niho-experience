# 公開受入と配備・停止の手順

[#15](https://github.com/niho-coliving/niho-experience/issues/15) の受入計画。窓口は担当1（サイト・デザイン）。各担当が自分の証跡を揃え、プレビューでの確認と本番での結果を分けて記録する。証跡に個人情報・token・管理画面のURLを貼らない。

## 公開の区切り

| 区切り | 状態 | 前提 |
| --- | --- | --- |
| モックプレビュー | 合成データで全画面・全状態を確認できる。予約は受け付けない | このリポのCIが通ること（済） |
| 既存拠点の試験販売 | NIHO既存拠点の体験を、ゲスト予約〜決済〜確認まで販売 | 連携A（niho-app#19122）、商品条件（#13）、検索・計測（#12・#14）、下記の受入 |
| 外部提供者も使えるv1 | 外部の提供者が自分で登録・出品できる | 上記＋連携B（niho-app#19123）、提供者登録の受入 |

試験販売ができても、連携Bの受入が済むまではv1の完了として扱わない。

## 受入項目

凡例：画面＝担当1、連携＝担当2、商品＝担当3、オーナー＝最終判断。「自動」はCIで毎回確認している項目。

### 画面・体験

| 項目 | 担当 | 確認方法 |
| --- | --- | --- |
| 360px・320px・デスクトップで一覧→詳細→予約入力→NIHOのcheckoutへ進める | 画面 | 自動（E2E）＋実機（iPhone Safari・Android Chrome）で1回ずつ |
| JST・円・料金単位・総額・販売者・取消条件が決済前に分かる | 画面・商品 | 実商品のページで目視 |

| キーボード・focus・コントラスト・代替文 | 画面 | 自動（axe WCAG 2.2 AA）＋実商品の写真の代替文を目視 |
| 表示速度：トップと詳細が携帯回線で実用的に読める | 画面 | 本番相当環境でLighthouse（モバイル）を記録 |

| 項目 | 担当 |
| --- | --- |

| 価格改ざん・販売停止・在庫競合・二重送信をAPIが拒否する | 連携 |

| 外部提供者：登録、既存口座の再利用、新規口座、他人の原稿・予約・売上に触れない | 連携（v1） |

### データ保護・公開範囲

| 項目 | 担当 | 確認方法 |
| --- | --- | --- |
| 予約入力・tokenがURL・ブラウザ保存・ログ・計測に出ない | 画面 | 自動（E2E）＋本番相当でCloud Runログを確認 |
| 予約関連ページが `no-store`・`noindex`、Cloudflareでcacheされない | 画面 | 応答ヘッダーとCloudflareのcache状態を確認 |

| ビルド・CIにsecretがなく、外部PRが配備権限に触れない | 画面 | CI設定の確認 |

## 配備（Cloud Run）

[ADR 0001](adr/0001-web-stack.md) の構成。初回のGCP・Cloudflareの準備はオーナーの承認後に行う。

1. mainのレビュー済みcommitを決める。
2. secretを持たないジョブがそのcommitからイメージを作る（`docker build .`）。同じジョブで `scripts/container-smoke.sh` を通す。
3. 保護された環境（承認者付き）のジョブが、OIDCでGCPに認証し、イメージを登録して新しいrevisionを**トラフィック0%** で作る。
4. revision専用URLで主要ページを確認する（トップ・詳細・予約入力の表示まで。本番で決済はしない）。
5. トラフィックを新revisionへ移す。Cloudflareでは静的ファイル以外のcacheを使っていないので、通常はpurge不要。
6. 15分ほどエラー率とログを見る。

環境変数（本番）：`EXPERIENCE_API_MODE=http`、`NEXT_PUBLIC_NIHO_WEB_ORIGIN`、`SITE_URL`、`SITE_INDEXING=allow`（受入後）、`BOOKINGS_ENABLED=true`、`HOST_SIGNUP_MODE`、NIHO側の遷移先URL。API接続の資格情報が必要になった場合はSecret Managerから渡し、イメージやリポには入れない。

## 戻す

- Cloud Runで直前のrevisionへトラフィックを戻す（数十秒）。
- このサイトは予約・決済の正本を持たないので、画面を戻しても成立済みの予約・返金はNIHO側で追跡できる。
- APIの互換性を壊す変更は、API側を先に配備しておく（#7の約束）。

## 障害時に予約を止める

1. **サイト側**：Cloud Runの環境変数 `BOOKINGS_ENABLED=false` で新しいrevisionを出す。詳細ページの予約欄と予約入力が「Online booking is paused for now」になり、決済へ進めなくなる。閲覧は続けられる。
2. **API側（正本）**：販売停止や受付停止は、NIHOの共通基盤で止める。サイトのスイッチは画面上の案内で、APIを止める代わりではない。
3. 状況と再開予定を担当とオーナーで共有する。再開は `BOOKINGS_ENABLED=true` に戻す。
4. 停止中に決済まで進んでいた予約は、NIHOの台帳で確認し、必要なら返金する（連携側の手順）。

## 記録

受入時は、確認した日・環境（プレビュー / 本番）・commit SHA・結果・確認者をIssueに残す。本番で受入が済むまで #15 を完了にしない。
